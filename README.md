# KDS для Poster: бары и рестораны

Система экранов заказов для заведений на Poster. Одна установка обслуживает сколько угодно заведений, и каждое подключается само через «Войти через Poster».

- **Станции:** кухня, бар, горячий и холодный цех, кондитерская. У каждой станции свой экран, а позиции расходятся по цехам Poster автоматически.
- **Раздача:** видит заказ целиком со всех станций и отмечает, кто отдал его гостю.
- **Учёт:** по каждой порции записано, кто продал, кто взял, кто приготовил и кто отдал. Отчёты строятся для сдельной зарплаты.
- **Устройства:** любой планшет, телефон, ТВ или ПК, просто в браузере.

| Адрес | Для кого |
|---|---|
| `/` | Публичная страница с кнопками «Подключить ресторан» и «Подключить бар» |
| `/admin/` | Администратор заведения: отчёты, станции, сотрудники, ставки, экраны |
| `/kds/` | Экран станции или раздачи |
| `/platform/` | Владелец платформы: все заведения, их состояние, ручное добавление |

## Как это работает

```
Кассы Poster заведения A ┐                              ┌► экран «Кухня»
Кассы Poster заведения B ┼► вебхук (по полю account)     ├► экран «Бар»
          ...            ┘  + опрос каждые 4 с          ├► экран «Раздача»
                             + сверка каждые 60 с        └► админка: отчёты
                                    │
                    сервер: на каждое заведение свой поток синхронизации;
                    состав чека в Poster сверяется с экранами, применяется разница
                                    │
                               PostgreSQL (у каждой строки свой account_id)
```

**На какую станцию идёт позиция.** Каждый товар в Poster привязан к цеху. Станция выбирается так:
1. Станция, у которой этот цех отмечен явно (вкладка «Станции»).
2. Иначе станция с похожим названием: «Кухня» ↔ «Кухня горячая», «Бар» ↔ «Бар». Часто это работает вообще без настройки.
3. Иначе станция, которой не подошло ни одно название: она забирает все остальные цеха.
4. Иначе позиция ни на какой экран не попадает, и админка показывает предупреждение «Цеха без экрана».

**Одна порция — одна строка.** Три мохито — три строки, их могут сделать разные люди. На кухне можно включить группировку («Бургер ×4»): одно касание отмечает всю группу, но каждая порция всё равно записывается отдельно.

| Действие | Что записывается |
|---|---|
| Касание новой позиции | «Взял: Мария» и время |
| Повторное касание | «Готово: Мария», время, ставка на этот момент |
| Касание чужой позиции | после подтверждения засчитывается тому, кто отметил; в журнал пишется «перехват» |
| «Всё готово» | все оставшиеся позиции заказа на этой станции |
| «Отдано» на раздаче | кто отдал заказ и когда |
| Отмена своей отметки | в течение 5 минут, только тем же сотрудником |

**Помощь на станции:**
- **Σ Сводка** сбоку: сколько всего сделать по всем открытым заказам («Мохито ×5, в работе 1»). Касание по строке подсвечивает заказы с этой позицией. Вкладка «Ингредиенты» суммирует техкарты Poster: «Ром 250 мл, лайм 2,5 шт».
- **Рецептура** (кнопка «i» у позиции): состав из техкарты Poster, сразу пересчитанный на нужное количество порций, фото и заметка заведения («как подавать»).
- **Таймер у каждой порции:** «0:45 / 1:30» от «взял» до нормы, краснеет при превышении. Норму можно не вводить: кнопка «Заполнить нормы по факту» возьмёт время, за которое делали 75% порций за 30 дней. В отчётах видно, какая доля порций уложилась в норму, по сотрудникам и по позициям.
- Комментарии про аллергию выделяются красным, модификаторы «без …» тоже.

**Если позицию убрали из чека,** порции отменяются в таком порядке: сначала не начатые, потом взятые, потом готовые. Готовая, но удалённая порция помечается «сделано → удалено» и попадает во вкладку «Контроль».

## Фастфуд

Формат «Фастфуд» (при подключении или в «Настройках»):

- **Номера вместо столов.** На кухне вместо стола крупно стоит номер заказа (последние три цифры чека) и пометка «С собой», «В зале» или «Доставка».
- **Оплаченные сразу чеки.** Чек закрывается на кассе раньше, чем его увидел экран, но всё равно приходит на кухню за 4–5 секунд.
- **Экран выдачи для гостей** (`/pickup/`): телевизор у стойки с колонками «Готовится» и «Готово — заберите» и сигналом, когда номер готов. Ссылка — в «Экраны и кассы».

Пошаговый запуск: [docs/LAUNCH_FASTFOOD.md](docs/LAUNCH_FASTFOOD.md).

## Внутри Poster

- **Кнопки в кассе Poster.** «Готовность» в окне заказа показывает официанту, что готово и кто делает. «KDS» в «Функциях» открывает экран станции прямо в кассе. При закрытии чека касса мгновенно сообщает KDS. Сборка, загрузка и подключение кассы по коду описаны в [pos-app/README.md](pos-app/README.md).
- **Админка KDS внутри админки Poster.** Приложение из маркетплейса открывается во встроенном окне, вход через Poster (`/auth/poster/manage`). Куки настроены для работы во встроенном окне (`SameSite=None; Secure; Partitioned`), а показ страниц разрешён только внутри Poster (`frame-ancestors`).

Планшеты и кассы подключаются **6-значным кодом** из админки: «Экраны и кассы» → «+ Экран» или «+ Касса Poster». Код действует 15 минут и срабатывает один раз. Если выдать новый код, после подключения по нему старое устройство отключится.

## Отчёты

- **Кто приготовил:** порции, начислено по ставкам, станции, среднее время. Есть фильтр по станции.
- **Станции:** нагрузка, среднее время, время, быстрее которого готовятся 90% заказов (видно узкие места).
- **Раздача:** кто отдал заказы и сколько готовая еда ждала на раздаче.
- **Продажи:** кто пробил, сколько закрыто чеков, оплаченная сумма, средний чек. Данные из закрытых чеков Poster.
- **Позиции** и **все порции:** полная детализация, видно кто продал, взял, сделал и отдал.
- **Контроль:** сделано и удалено из чека, зависшие порции, перехваты, ручные исправления.
- Всё выгружается в Excel. Период считается рабочими днями (с 06:00 до 06:00, настраивается). Ставка фиксируется в момент отметки, поэтому изменение ставок не пересчитывает прошлую зарплату.

## Запуск

Одна команда на чистом Ubuntu/Debian ставит Docker, генерирует секреты и запускает систему. Её же можно запускать повторно для обновления: данные и пароли сохраняются.

| Где | Команда | Адрес |
|---|---|---|
| Облачный сервер со своим доменом | `sudo DOMAIN=kds.example.com ./install.sh` | `https://kds.example.com` |
| Облачный сервер, **временный домен** | `sudo ./install.sh` | `https://<ip-сервера>.sslip.io`, с настоящим HTTPS-сертификатом, без покупки домена |
| **Мини-ПК в самом заведении** (локально) | `sudo MODE=local ./install.sh` | `http://<ip-в-локальной-сети>/` |

Временный домен вида `1-2-3-4.sslip.io` указывает на IP сервера, и Caddy сам получает для него сертификат Let's Encrypt. Когда появится свой домен, перезапустите с `DOMAIN=…`.

**Локальный режим** подходит, если интернет в заведении нестабилен или облачный сервер не нужен. Экраны работают по Wi-Fi напрямую с мини-ПК, задержка минимальная. Заказы из Poster всё равно приходят через интернет, потому что Poster облачный: при обрыве связи экраны показывают уже полученные заказы и принимают отметки, а новые заказы догонят их, как только связь вернётся. Закрепите за мини-ПК постоянный IP в роутере.

### Что делает систему устойчивой

- **Автозапуск.** Все контейнеры поднимаются сами после сбоя, перезагрузки и отключения питания (`restart: always`, Docker включён в автозагрузку).
- **Зависание.** Если приложение перестало отвечать на `/health`, отдельный контейнер `autoheal` перезапускает его.
- **Порядок запуска после отключения питания.** Приложение ждёт базу данных и не уходит в цикл падений. Caddy начинает принимать запросы только после того, как приложение здорово.
- **Логи** не забьют диск: по 3 файла × 10 МБ на контейнер. Старые сырые вебхуки удаляются через 14 дней.
- **Резервная копия базы — каждые сутки**, хранится 30 дней. Неудачная копия не затирает удачную.
- **Время** синхронизируется по NTP: от него зависят таймеры, отчёты и сертификаты.

**Обслуживание:**
```bash
./scripts/doctor.sh                              # состояние: контейнеры, Poster, диск, копии, время
sudo ./scripts/restore.sh backups/kds_….sql.gz   # восстановить базу (текущая сохраняется перед этим)
docker compose logs -f app                       # журнал приложения
```

### Вариант 1. Платформа для многих заведений

1. На dev.joinposter.com создайте приложение. Redirect URI: `https://ваш-домен/auth/poster/callback`. Вебхуки: `https://ваш-домен/webhooks/poster`, подписка на чеки (`transaction`), товары и сотрудников.
2. В `.env` укажите `POSTER_APP_ID` и `POSTER_APP_SECRET`.
3. Заведение открывает главную страницу и нажимает «Подключить ресторан» или «Подключить бар». После входа в Poster оно сразу попадает в свою админку с готовыми станциями.
4. Все заведения видны в `/platform/`: работает ли синхронизация, когда экраны последний раз были онлайн, сколько порций за сутки. Там же можно открыть админку любого заведения, чтобы помочь с настройкой.

### Вариант 2. Одно заведение без приложения

Укажите в `.env` `POSTER_TOKEN` (Poster → «Доступ → Интеграция»), `POSTER_ACCOUNT`, `ADMIN_PASSWORD` и `VENUE_TYPE` (`bar`, `restaurant` или `fastfood`), или передайте их прямо установщику: `sudo POSTER_TOKEN=… POSTER_ACCOUNT=… VENUE_TYPE=fastfood ./install.sh`. При первом запуске заведение создастся само. Заведения с токеном можно добавлять и вручную через `/platform/`.

### Настройка заведения (админка)

1. **Станции:** проверьте, что напротив каждой станции в блоке «Сейчас сюда идут» стоят нужные цеха. Добавьте свои станции, например «Холодный цех» или «Пицца».
2. **Сотрудники:** отметьте тех, кто работает на экранах, и выдайте PIN.
3. **Ставки:** сдельная ставка за порцию, видно по станциям.
4. **Экраны:** создайте экран для каждой станции и откройте выданную ссылку на самом устройстве.
5. **Настройки:** как экран называет сотрудников («Бармен», «Повар»), таймеры, пароль админки.

### Что проверить на реальном аккаунте Poster

Интеграция написана по документации API Poster, но на живом аккаунте её ещё не проверяли. Названия полей у разных версий API немного отличаются, поэтому все чтения идут через `src/poster/normalize.js` с запасными вариантами. Сырые ответы сохраняются в `transactions.raw` и `webhook_log`.

- [ ] Вход через Poster: адреса OAuth и поля ответа совпадают с текущей документацией. Адреса меняются переменными `POSTER_OAUTH_AUTHORIZE_URL` и `POSTER_OAUTH_TOKEN_URL`.
- [ ] Во вебхуке есть поле `account`, по которому определяется заведение.
- [ ] Стол, официант, касса и модификаторы отображаются правильно.
- [ ] Суммы в «Продажах» совпадают с Poster (`POSTER_MONEY_DIVISOR`).
- [ ] Техкарты: `menu.getProduct` отдаёт `ingredients`, единицы и вес на одну порцию (`normalizeRecipe`), фото открывается.
- [ ] Подпись вебхуков проходит (вкладка «Состояние»). После этого включите `POSTER_WEBHOOK_STRICT=true`.

**Когда заказ появляется на экране** (Настройки): сразу, как позицию пробили в чек, или только после кнопки «Отправить в цех» в Poster. Во втором режиме оплаченный чек появляется на экране, даже если его не отправляли в цех: так работает быстрое обслуживание.

Что подтверждено по API Poster и что осталось проверить на живом аккаунте: [docs/POSTER_API.md](docs/POSTER_API.md).

## Надёжность и изоляция

- Источник истины — Poster: каждое событие перепроверяется запросом к API. Сверка идемпотентна, поэтому вебхук, опрос и полная сверка одного чека не создают дублей.
- Одновременные нажатия двух человек засчитываются ровно одному (блокировки строк в PostgreSQL).
- Если на планшете пропал Wi-Fi, нажатия копятся и отправляются позже, без задвоения: у каждого нажатия свой `op_id`.
- Заведения полностью изолированы: данные, PIN-коды, экраны, сотрудники и отчёты. Одинаковые номера чеков в разных аккаунтах Poster не пересекаются. Это покрыто тестами.
- Сбой связи с Poster у одного заведения не влияет на остальные.
- Любое действие пишется в журнал: кто, когда, с какого экрана.

## Стабильность

**Уведомления в Telegram.** Один бот на всю установку (`TELEGRAM_BOT_TOKEN`). Заведение подключает свой чат в «Настройки → Уведомления в Telegram»: одноразовый код, ссылка на бота, «Start». Ваш чат `TELEGRAM_PLATFORM_CHAT_ID` получает тревоги всех заведений с названием. Каждая тревога приходит один раз, когда проблема началась, и ещё раз, когда она закончилась:
- нет связи с Poster больше 3 минут;
- экран не на связи больше 5 минут, но только пока в заведении идут заказы (ночью после закрытия тревог нет);
- порция не готова дольше 30 минут.

**Сервер:**
- Пока Poster не отвечает, опрос замедляется вдвое за каждую неудачу, до раза в минуту. Первый же успешный ответ возвращает обычную частоту. Заведения стартуют вразнобой, а не все в одну секунду.
- У соединений с базой есть таймауты, а обрыв соединения не роняет процесс. При непредвиденной ошибке процесс перезапускается (Docker `restart: always`).
- Каждый день в начало рабочего дня система заново читает из Poster закрытые чеки за двое суток и исправляет расхождения до того, как кто-то построит отчёт по зарплате.
- `/health` проверяет базу и отвечает 503, если она недоступна. Подключите его к UptimeRobot или Healthchecks.

**Экраны:**
- После выхода новой версии экраны перезагружаются сами. Неотправленные нажатия не теряются: экран перезагрузится, только когда очередь опустеет.
- Если экран 90 секунд не может обновиться при живой сети, он перезагружается сам, но не чаще раза в 5 минут.

**Вне кода:** база с резервными копиями на другом сервере и проверкой восстановления, внешний мониторинг `/health`, планшеты в режиме киоска на зарядке, резервный 4G-роутер или печать бегунков в цех на время пилота, тестовое заведение для обновлений.

## Разработка

```bash
npm install
npm test                      # нужен PostgreSQL с базой kds_test (DATABASE_URL)
npm run mock-poster           # имитация Poster на :4100
POSTER_API_URL=http://localhost:4100/api npm start
# затем в /platform/ добавить заведение с любым токеном
npm run simulate              # случайные заказы в имитацию
```

```
src/accounts.js  заведения и их стартовые станции (bar / restaurant)
src/poster/      клиент API Poster, OAuth, нормализация полей, вебхуки
src/sync/        reconcile.js: сверка чека и выбор станции; engine.js: синхронизация каждого заведения
src/units.js     действия на экранах: взял, готово, вернул, отдано
src/kitchen.js   сводка «сколько сделать», рецептура, нормы времени по факту
src/alerts.js    уведомления в Telegram и привязка чатов заведений
src/reports.js   отчёты и CSV
src/app.js       HTTP API: экраны, админка, платформа, OAuth, вебхуки
public/          главная, экран KDS (PWA), админка, панель платформы
test/            тесты и имитация Poster
```
